Plano de ajustes · Barroso Harness v0.1.0-bh.56 · 2026-10-20

Performance: prompt, cache e tools

O que as fontes oficiais e as harnesses maduras recomendam, onde o BH está hoje e uma sequência de mudanças em fases. Copiamos do OpenCode o que dá ganho mensurável, sem replicar a arquitetura inteira.

Resumo. A lentidão medida vem quase toda do tempo de pensamento do modelo: ~2199 s de modelo contra ~26 s de tools numa sessão real. Isso vem do número de rodadas e do tamanho de cada request, não de tool faltando. Há três alavancas, em ordem de retorno:
  1. Prefixo estável e cache visível. Cada rodada deve reaproveitar o prefixo já processado.
  2. Catálogo de tools enxuto. Divulgação progressiva das tools MCP e de gestão.
  3. Menos rodadas. Esforço adequado, tools que resolvem em uma chamada e saídas curtas.
Tudo começa por medir, porque hoje o BH não lê os tokens em cache que o provider devolve.

Além da performance, o plano cobre:
  • Gestão completa pelo agente: criar, editar e remover skills, MCP e BARROSO.md (Fase 5).
  • Propagação imediata dessas mudanças para todas as sessões abertas, via eventos [system update] append-only (Fase 6).

0. Validação final (2026-10-20)

Conferi cada ponto contra a documentação oficial e contra o que o Claude Code faz. Também testei direto no provider em uso (Nous, z-ai/glm-5.3-flash). A linha geral se confirma, mas três pontos mudaram por causa das medições.

Confirmado nas fontes:

  • Claude Code:
    • Por padrão adia todas as tools MCP: no início vão só os nomes e as instruções de cada servidor.
    • Tem um modo auto que só adia acima de 10% da janela de contexto.
    • Avisa o modelo quando um servidor falha.
    • Reage a list_changed recarregando a lista do servidor.
    • Salva em arquivo resultados de tool acima de 50k caracteres e devolve a referência.
  • Anthropic: a tool search reduziu ~85% dos tokens e subiu o acerto (Opus 4.5 de 79,5% para 88,1%). Abaixo de ~10 tools não compensa.
  • Z.ai: o cache do GLM é implícito e reportado em prompt_tokens_details.cached_tokens, e qualquer diferença de formatação o quebra.
  • MCP spec: servidores com listChanged enviam notifications/tools/list_changed, e o cliente deve chamar tools/list de novo. Isso entra na Fase 6.

2. Diagnóstico do BH hoje

Já está bom

  • A ordem dos MCP é determinística (mcpManager.order). A injeção é append-only e o catálogo é montado em ordem fixa.
  • O histórico é append-only (Mensagem é byte-determinística, sem maps).
  • O system prompt tem só a data, sem hora, então muda no máximo uma vez por dia.
  • Tools paralelas, grep/glob/edit e uma política de tools explícita já foram entregues.

Onde perde tempo e tokens

  • Cache invisível. dealer.Usage só lê prompt_tokens, então não dá para saber se há cache hit.
  • Data e cwd no meio do system. Ficam antes da política e do BARROSO.md, e a troca de dia invalida o system inteiro.
  • Catálogo cheio a cada rodada. Vão sempre built-ins, gestão (mcp_add/remove, skill_create/remove), contexto, web e todas as tools MCP (Playwright sozinho tem dezenas, com schemas grandes).
  • Ordem de chaves no schema. O map[string]any de toolSchemas() é ordenado pelo encoding/json, o que é estável. Os schemas MCP repassados do servidor também precisam continuar estáveis.
  • Effort "max" configurado como padrão: cada rodada pensa o máximo, inclusive rodadas triviais como ler arquivo.
  • Não há prompt_cache_key e o catálogo muda quando um MCP cai ou volta.

3. Plano em fases

Fase 0 — Medir antes de mexer obrigatório ~0,5 dia

  • Em dealer.go, ler usage.prompt_tokens_details.cached_tokens (OpenAI e compatíveis) e cache_read_input_tokens/cache_creation_input_tokens quando vierem. Expor em Usage.CachedTokens.
  • Registrar por rodada: tempo até o primeiro token (TTFT), tempo total, tokens de prompt/cache/saída, bytes de tools e bytes de system. Gravar no evento da sessão em SQLite e mostrar cache NN% no painel lateral, junto do contexto.
  • Criar bh bench: 5 tarefas fixas (explorar repo, corrigir bug, rodar testes, editar multi-arquivo, pergunta simples) com relatório de rodadas, tempo e tokens. Toda fase seguinte é aceita ou rejeitada por esse número.

Aceite: hit rate de cache e TTFT visíveis por rodada; baseline salvo em docs/bench/.

Fase 1 — Prefixo estável ganho alto, risco baixo ~0,5 dia

  • Reordenar systemPrompt(): identidade e tool policy e working style (estáticos) → BARROSO.md global → BARROSO.md do projeto → no fim o ambiente (OS, shell, cwd, data).
  • Congelar a data no início da sessão (não usar time.Now() a cada ciclo). Se o dia virar no meio de uma sessão longa, isso entra como mensagem de sistema nova, nunca editando o system.
  • Garantir que o catálogo de tools seja byte-idêntico entre rodadas:
    • Ordenação fixa, já verdadeira.
    • Serialização canônica dos schemas MCP com chaves ordenadas.
    • Um MCP que cai mantém as tools no catálogo e devolve erro acionável ("server X disconnected"), em vez de sumir e reaparecer.
  • Enviar prompt_cache_key: removido após o teste. Não deu ganho no provider atual.
  • Nesse provider as tools vêm antes do system no prompt. Por isso a lista de tools é o item mais sensível ao cache: qualquer mudança nela zera o cache inteiro.
  • Para providers Anthropic nativos (futuro): breakpoints cache_control no fim das tools, no fim do system e na última mensagem estável.

Aceite: rodadas 2+ de uma mesma tarefa com cache ≥ 80% dos tokens de prompt (quando o provider tem cache) e TTFT menor no bench.

Fase 2 — Catálogo progressivo ganho alto risco médio ~2 dias

É aqui que o BH se aproxima do OpenCode sem copiar o Code Mode. Fica em duas camadas:

CamadaConteúdoComo vai ao modelo
Direta (sempre)file_read, file_write, edit, grep, glob, terminal_run, task_spawn, skill_read, web_search/fetch e tool_searchFunction tool completa, como hoje.
Sob demandaTodas as tools MCP; gestão (mcp_add/remove/list, skill_create/remove); contexto vivo e compactação quando não usadosLinha compacta no catálogo do system (nome — descrição ≤120 chars, agrupada por servidor, orçamento de ~2k tokens). O schema completo vem por tool_search.
  • Mecânica compatível com qualquer provider OpenAI-like:
    • tool_search(query) devolve nome, descrição e schema das tools que casam (BM25 simples em Go, sem dependência nova).
    • O schema descoberto chega como resultado de tool, ou seja, no histórico, que é append-only.
    • A chamada passa por tool_call(name, args), um proxy fixo: o runtime valida os argumentos contra o schema e executa.
    • A lista de functions nunca muda durante a sessão. Isso foi validado no teste: acrescentar uma tool zera o cache. É o mesmo princípio do execute do OpenCode, sem o runtime JS.
  • Atalho: uma tool cuja linha compacta já basta para o modelo pode ser chamada direto via tool_call, sem uma rodada de busca.
  • Limiar automático: se o catálogo total couber em ~8k tokens, manda tudo direto, como hoje. Só ativa a camada sob demanda acima disso. Configurável e desligável (tool_disclosure: auto|full|progressive), sem teto artificial.
  • Providers Anthropic nativos: usar defer_loading: true + tool_search_tool_bm25 do servidor em vez da busca local.

Aceite: com Playwright + memory ligados, bytes de tools por rodada caem ≥ 70%, e o bench não tem queda de acerto nem aumento de rodadas acima de 10%.

Fase 3 — Qualidade das tools ganho médio ~1 dia

  • Revisar as descrições de built-ins no estilo "explicar a um novato". Para cada tool: quando usar, quando NÃO usar, formato de path, limites de saída, um exemplo.
  • Saídas de tools mais curtas:
    • grep/glob paginados com contagem total e dica de refino.
    • terminal_run guarda o output completo como blob e devolve as últimas N linhas mais o caminho do blob.
    • file_read com ranges.
    Erros sempre com a próxima ação sugerida.
  • Prefixar tools MCP por servidor (playwright_browser_click), como o padrão de namespacing recomendado. Isso melhora a busca da Fase 2.
  • Remover sobreposições, como tools de contexto vivo que duplicam grep/file_read.

Aceite: menos chamadas por tarefa no bench e nenhuma tool com descrição de uma linha só.

Fase 4 — Menos rodadas e esforço adequado ganho alto em latência ~1 dia

  • O effort é decidido pelo bench, não por suposição. O teste mostrou que medium pensa ~10× menos que high/max, e que omitir o campo pensou mais que max. O bench roda as 5 tarefas em medium, high e max, e o padrão passa a ser o mais rápido que mantiver o mesmo acerto. O usuário continua escolhendo via /effort. O effort só muda entre turnos, nunca dentro do ciclo.
  • Instruções de política já existentes ficam mais firmes no prompt estático: chamadas paralelas, batch de leituras e "planeje antes, depois aja".
  • Instruções que mudam na sessão (skill ativada, BARROSO.md editado, MCP adicionado) entram como mensagem [system update] no fim do histórico, como os deltas do OpenCode. O system de topo não é editado.
  • Compactação: preservar o prefixo e resumir só o miolo, para manter o cache do system e das tools.

Aceite: tempo total do bench menor, com o mesmo resultado.

Fase 5 — Gestão completa de skills, MCP e BARROSO.md pelo agente requisito ~1,5 dia

Hoje o BH tem skill_create (que também substitui) / skill_remove e mcp_list / mcp_add (que também substitui) / mcp_remove. Editar exige reescrever o recurso inteiro, e não há tool para o BARROSO.md. O conjunto final fica assim:

RecursoToolsComportamento
Skillsskill_create, skill_edit, skill_remove (+ skill_read, skills_list)skill_edit é uma edição parcial:
  • Muda só o description, ou
  • substitui um trecho exato do corpo (old_string → new_string, como a tool edit), ou
  • troca o corpo inteiro.
Pode mudar o escopo (projeto ↔ global) e renomear. skill_create falha se a skill já existe, para evitar sobrescrita acidental; o erro aponta para skill_edit.
MCPmcp_add, mcp_edit, mcp_remove (+ mcp_list)mcp_edit faz patch dos campos informados: command, args, env, url, headers, renomear. Também tem enabled e reconnect: true. Salva no config.json e reconecta só aquele servidor. mcp_add falha se o nome já existe. mcp_list mostra o estado (conectado/erro) e a contagem de tools.
BARROSO.mdinstructions_read, instructions_write, instructions_edit, instructions_deleteEscopo global (~/.barroso-harness/BARROSO.md) ou project (cwd ou o BARROSO.md ancestral mais próximo). read mostra os arquivos que se aplicam e a precedência. write cria ou reescreve. edit faz substituição exata de trecho. delete apaga o arquivo.
  • Todas essas tools ficam na camada sob demanda da Fase 2, e continuam disponíveis ao modelo sem pesar no prefixo.
  • Rodam sempre sequencialmente (como hoje em sequentialTools) e devolvem um diff curto do que mudou.

Fase 6 — Propagação imediata para todas as sessões requisito risco médio ~2 dias

Qualquer alteração em skills, MCP ou BARROSO.md vale na próxima rodada de todas as sessões abertas, inclusive as de outros processos bh e o ACP. Sessões novas não são o único alvo. O histórico continua append-only: a mudança chega como evento na conversa, e o system prompt não é editado.

  1. Registro de revisões.
    • Cada tool de gestão (e os comandos /mcp, /skills da UI) grava uma linha numa tabela resource_changes do SQLite compartilhado: revisão, recurso, ação, nome, escopo e cwd do projeto.
    • Edições feitas à mão (o usuário abriu o BARROSO.md no editor, ou mudou o config.json) são detectadas por fingerprint: mtime, tamanho e hash dos arquivos relevantes, checados no início de cada rodada. A checagem custa microssegundos e não traz dependência nova.
  2. Checagem na fronteira de rodada. Antes de cada request ao modelo, a sessão compara a última revisão vista e o fingerprint. Se algo mudou e é relevante para ela (global, ou o mesmo projeto):
    • BARROSO.md: resolve de novo e acrescenta uma mensagem [system update] BARROSO.md (project) changed: com o diff ou o texto novo. O system de topo fica congelado no conteúdo do início da sessão; quem vale é o mais recente que aparece nos updates. O prompt fixo diz isso ao modelo.
    • Skills: atualiza a listagem e acrescenta [system update] skill X created/edited/removed. Um /X usa sempre o SKILL.md atual.
    • MCP list_changed: quando o próprio servidor avisa que suas tools mudaram, o BH chama tools/list de novo e segue o mesmo fluxo de evento. Se o refresh falhar, mantém as tools anteriores, como faz o Claude Code.
    • MCP: cada processo reconcilia os próprios clientes com o config.json: conecta os novos, reconecta os editados e fecha os removidos. Em seguida atualiza o catálogo sob demanda e acrescenta [system update] MCP X added (N tools: …). Tools de servidor removido passam a devolver erro acionável. Com a Fase 2, a lista de tools diretas não muda, então o cache do prefixo é preservado. Antes da Fase 2, cada mudança de MCP custa uma rodada sem cache, porque a lista de functions muda. Isso é aceitável, já que mudanças de MCP são raras.
  3. Sessão ocupada. O update entra na próxima fronteira de rodada do turno em andamento, no mesmo ponto seguro usado pelo steer da fila. Não interrompe uma tool rodando.
  4. Sessão ociosa e UI. A tela mostra uma linha discreta na conversa (↻ MCP playwright updated) e atualiza o painel lateral (MCPs, skills) na hora, sem esperar o próximo envio. Isso usa notificação por polling leve da revisão (1–2 s) no processo da TUI.
  5. Resume. Ao retomar uma sessão, o mesmo mecanismo compara a revisão salva na sessão com a atual e acrescenta um update único com tudo que mudou nesse meio-tempo.
  6. Persistência. As mensagens [system update] ficam no histórico da sessão, como as demais. A tela as desenha como evento, não como fala do usuário.

Aceite (teste de integração com 2 processos):

  • A sessão A cria, edita e remove uma skill, um MCP e o BARROSO.md.
  • A sessão B, ociosa e depois ocupada, recebe o evento na rodada seguinte e usa o recurso novo sem reiniciar.
  • Uma edição manual do BARROSO.md também propaga.
  • O hit rate de cache do prefixo não cai após a mudança.

4. O que NÃO copiar do OpenCode

  • Code Mode completo (um runtime JS executando scripts de tools). É custo alto e risco alto. O ganho principal, o catálogo enxuto, vem da Fase 2 com muito menos código.
  • Tirar do modelo a gestão de skills/MCP/instruções. É uma vantagem do BH: ela é ampliada (Fase 5) e passa da camada direta para a sob demanda.
  • Agents com system substituível, LSP, etc. Fora do escopo de performance.

Sugestão:

  • Release 1: 0 → 1 → 4, e medir.
  • Release 2: 5 → 6. A Fase 6 depende do congelamento do system da Fase 1 e do mecanismo de [system update] da Fase 4.
