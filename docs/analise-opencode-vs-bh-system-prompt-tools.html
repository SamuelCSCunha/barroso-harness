Análise de arquitetura · OpenCode v2.0.32 · Barroso Harness v0.1.0-bh.56

System prompt e ferramentas

Como cada harness monta instruções, revela ferramentas ao modelo e permite personalizar a própria harness — e por que essas escolhas produzem comportamentos diferentes.

Resumo executivo. O OpenCode divide as instruções em camadas: uma identidade estável, instruções configuráveis e atualizações incrementais durante a conversa. Também usa divulgação progressiva de tools para controlar o tamanho do catálogo. O BH monta uma única mensagem system e envia o catálogo completo de tools a cada ciclo. Em compensação, o BH dá ao modelo tools explícitas para criar/remover skills e adicionar/remover servidores MCP; o OpenCode deixa a gestão da configuração principalmente com o usuário.

1. Como o system prompt chega ao modelo

OpenCode v2: partes system separadas

O ponto de montagem é packages/core/src/session/model-request.ts → baseTranscript(). A lista system recebe duas partes principais:

  1. Identidade e regras hardcoded: packages/core/src/session/runner/prompt/system.txt, com orientação geral, comunicação, trabalho em codebase e interpolação de OPENCODE_TOOL_GUIDANCE.
  2. Baseline configurável: instruções renderizadas em packages/core/src/session/context.ts e session/history.ts.

Há uma exceção importante: se o agent selecionado define agent.system, esse texto substitui o system.txt padrão; não é apenas acrescentado a ele. O baseline continua separado.

Múltiplos SystemPart Pode atualizar durante a sessão

BH: uma string system

O ponto de montagem é internal/runtime/session.go → systemPrompt(). Cada ciclo do agente combina:

  1. Identidade e política de trabalho hardcoded, incluindo YOLO, ambiente real, shell, cwd, data, uso de tools e estilo de resposta.
  2. BARROSO.md, acrescentado como seção final, se existir.

internal/instructions/instructions.go busca BARROSO.md no diretório do projeto e nos pais; o global entra depois. Os textos são concatenados numa única string system. Skills, MCP e resultados de memória não são camadas system especiais: entram pelo catálogo de tools e pelo histórico.

2. Personalização: configuração, tools ou skills?

OpenCode: configuração e carregamento

  • System prompt e regras: AGENTS.md global/projeto, entradas instructions e configuração. O modelo não recebe uma tool core para editar essas regras.
  • Agents: arquivos/config podem definir system próprio, modelo, modo, limite de passos, cor e permissões. As permissões determinam indiretamente quais tools ficam disponíveis.
  • MCP: servidores vêm da configuração do usuário. O modelo pode usar tools/resources dos servidores já conectados, mas não tem tools core mcp_add/mcp_remove.
  • Skills: o modelo tem a tool skill para carregar as instruções e recursos de uma skill. Criar/remover skills não é oferecido como tool core.
  • Commands: slash commands são ações da interface do usuário; não são o mecanismo de gestão do catálogo de configuração pelo modelo.

BH: gestão explícita pelo agente

  • System prompt configurável: BARROSO.md global e por projeto complementa a instrução hardcoded. Não existe agent.system substituível.
  • Skills: skills_list/skill_read descobrem e carregam instruções; skill_create/skill_remove criam e removem SKILL.md. /nome expande uma skill em instruções no pedido do usuário.
  • MCP: mcp_list/mcp_add/mcp_remove permitem ao modelo inspecionar e gerir servidores na própria sessão.
  • Subagentes: task_spawn dispara tarefas paralelas, e resultados chegam à sessão principal.
  • BARROSO.md: não é uma skill nem uma tool. É um arquivo que o runtime concatena à mensagem system.
Diferença conceitual: skill fornece procedimento e contexto especializado; tool executa uma operação. No OpenCode, a tool skill carrega uma skill, mas a configuração de MCP/skills permanece essencialmente no plano do usuário. No BH, criar/remover skills e adicionar/remover MCP são operações que o modelo pode chamar como tools. Isso dá ao agente mais autonomia de configuração, mas também coloca essas capacidades no catálogo de tools de cada ciclo.

O que “descrição completa” significa na prática

No OpenCode, não é correto dizer simplesmente “manda tudo” ou “manda só frontmatter”. As tools diretas recebem descrição e schema completos. Para tools sob Code Mode, o modelo vê primeiro uma listagem compactada, com assinaturas conforme o orçamento de tokens, e pesquisa uma assinatura completa via search dentro do execute quando necessário. A tool search não é uma segunda function exposta ao provider: ela vive no runtime Code Mode.

No BH, toolSchemas() monta para cada spec uma function com name, description e parameters vindos da spec. O request recebe a lista integral de built-ins, session tools, skills, web, contexto, MCP e subagentes disponíveis naquele ciclo. Os corpos das skills, porém, são carregados por skill_read; o catálogo não precisa despejar todo o conteúdo de cada SKILL.md.

5. Fontes no código

OpenCode v2.0.32

  • packages/core/src/session/model-request.ts — baseTranscript e partes system.
  • packages/core/src/session/system-prompt.ts e session/runner/prompt/system.txt — prompt base e orientação condicional de tools.
  • packages/core/src/session/context.ts, session/history.ts, session/instruction-state.ts — fontes e atualizações de instruções.
  • packages/core/src/config/plugin/instruction.ts — descoberta/precedência de instruções.
  • packages/core/src/tool.ts, tool/runtime.ts, codemode/catalog.ts, codemode/instructions.ts — classificação, schema e catálogo progressivo.
  • packages/core/src/tool/plugin/mcp-resource.ts, tool/plugin/skill.ts, config plugins MCP/agent/skill/provider.

Barroso Harness

  • internal/runtime/session.go — systemPrompt(), Session.SendWithImages(), toolSchemas() e ciclo.
  • internal/runtime/extras.go — toolCatalog(): built-ins, sessão, contexto, web, skills e injetadas.
  • internal/instructions/instructions.go — descoberta/concatenação de BARROSO.md.
  • internal/tools/specs.go e search.go — ferramentas core, grep/glob/edit.
  • internal/skills/tool.go e management.go — listar/ler/criar/remover skills.
  • internal/wiring/management.go — gestão MCP e injeção dinâmica de tools.
Conclusão: o OpenCode investe mais na separação entre política estável, instruções mutáveis e descoberta de tools com orçamento. O BH usa um prompt system único e um catálogo completo de tools por ciclo, mas permite ao modelo modificar MCPs e skills. Essas diferenças ajudam a explicar diferenças de tokenização e comportamento; nenhuma das arquiteturas é só “frontmatter versus descrição”.
Documento de análise produzido a partir do código-fonte local do OpenCode v2.0.32 e do Barroso Harness. Os caminhos e nomes citados são verificáveis nos repositórios; o tamanho de 2.000 tokens refere-se ao orçamento do catálogo inline Code Mode, não ao limite total do prompt.
